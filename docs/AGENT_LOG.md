## 2026-10-20 · claude · stack/m10/05-two-stage · #96
- Done: the two-stage compile (ADR 0013).
  - `renderFormula` takes a `Stage`: an aggregate becomes a column of `g`, or of `p` inside `PREVIOUSPERIOD`, and `RUNNINGSUM` becomes `sum(…) over (partition by <other dims> order by <time> rows between unbounded preceding and current row)`.
  - `compileQuery` builds `g`, then `p` over the window one bucket earlier: filters on the time axis's column compare `col + interval '1 <grain>'`, and quarters are 3 months. `p` is joined on `p.d + interval = g.d` and `is not distinct from` on the other dimensions. The outer query sorts (nulls last) and limits.
  - Queries without time functions take the old path, so their SQL is byte-identical.
- Tests: written first.
  - Golden SQL: `PREVIOUSPERIOD` with a shifted date filter, `RUNNINGSUM` partitioned by status, the join on other dimensions.
  - Integration (`time.test.ts`, CI): 300 sales on about half the days of a half-year. By day, week and month, with and without a region, each bucket's previous period equals the plain value one grain earlier and its running sum the plain values so far. A date filter's window still reads the month before, and a day after a gap gets no previous value.
- Scope/decisions: the policies and filters are bound again for each CTE. Changeset (gateway minor).
- Next: `ALL` for shares of a total (#97).

## 2026-10-17 · claude · fix/db-deadline · #70
- Done: the cause of the hang on fresh deployments, found with #59's watchdog, and its fix.
  - **Evidence:** on a preview deploy during the M6 merges (dpl_28mtyozW…, 21:37 UTC), six `/contract` and `/query` requests logged `request slow` at stage `contract`, then hit the 30 s cap. The contract's introspection query never answered. The pooler had shown such connections idle (2026-10-08 and 2026-10-17), so a first query through it can be lost. With one connection per instance, every later read waited behind it.
  - **Fix:** gateway reads (contract introspection, queries, health) get a 5 s deadline. A read that misses it gets a new connection (`postgresSource().reset()`) and one more try, logged as `database connection replaced`. Reads are idempotent.
- Tests (written first): a source whose first connection never answers still serves `/contract` once the connection is replaced; `reset` gives a new client; without `reset`, a stuck read fails the request at 5 s instead of hanging. The #59 watchdog test now uses a stuck `resolveScope`, which has no deadline.
- Scope/decisions: the demo's own `appDb` (memberships, dashboards) has no deadline yet; the evidence pointed at the source connection only.
- Next: watch the next deploys for `database connection replaced` and for timeouts.
